# Lens: semantics

Verdict: Sound after fixes. The core shadow mechanism is correct: I attacked the full duplicate-binding matrix (add/remove ladders with distinct-but-equal key objects, replace-then-remove, filter_map_inplace cascading pops, find_all ordering, copy with shared immutable stacks, clear/reset/to_seq staleness, nan keys, of_seq/add_seq randomization defaults, Make's randomize() immunity) and the design reproduces stdlib's observable behavior in every case for keys whose equal/compare is a hash-consistent equivalence relation with total compare — including the subtle ones (popped older key objects resurfacing exactly as stdlib's surviving cons cells; replace's in-place key-object overwrite; per-key most-recent-first everywhere; O(1) length = items + nshadow). The resize/shadow decoupling argument (shadow keyed by key, not slot) genuinely removes the recency-vs-rehash coupling and is the design's strongest point. Five serious issues need design-level changes before implementation, none fatal to the architecture: (1) rebuild must enumerate the source shadow hash-independently or it loses data in rebuild's one documented use case; (2) add-probes-equality must be promoted to a documented deviation (cyclic/functional keys: demonstrated stdlib-works/Swiss-hangs divergence); (3) traversal write-paths need a pinned capture discipline to actually deliver the promised memory safety; (4) ctrl-publish ordering plus a single swappable core record to avoid type-confusion regressions vs stdlib under unsynchronized misuse; (5) the asymmetric-equal replication claim must be re-scoped (counterexamples verified against the real stdlib both ways) and add's equality order specified. With those plus the minor fixes (create clamping, empty-stack-entry cleanup, the kind-ascription escape hatch), the design meets the contract it set out to satisfy.

## [SERIOUS] rebuild reads the source's shadow table through the current hash, silently dropping shadowed bindings in exactly rebuild's documented use case

**Scenario:** design.md §3 rebuild: "for each FULL slot of the source: re-insert oldest-first (List.rev (slot :: stack))". Obtaining `stack` is a shadow-table lookup keyed by the slot key, i.e. a hash-directed probe of the source's shadow table. But rebuild's documented purpose (api.md §2.15, mli:249-262; design.md §1 itself claims "rebuild re-imports such [marshaled] tables") is repairing tables whose stored layout no longer matches the current hash function — e.g. a Swiss table marshaled under OCaml version N and unmarshaled under N+1 where caml_hash changed (this is why rebuild was added in 4.12). In that scenario the source's flat slots are enumerated linearly (fine), but every shadow lookup probes with the NEW hash against a shadow table laid out by the OLD hash and misses: all shadowed duplicates are silently dropped from the rebuilt table (length shrinks, bindings lost). stdlib's rebuild (hashtbl.ml:786-800) never consults hash or equal on the source — insert_all_buckets walks the bucket array — so it handles hash changes perfectly. Note the seed is NOT the problem (the shadow table's own marshaled seed is self-consistent); only a change of the hash function itself triggers it — which is the one scenario rebuild exists for.

**Fix:** Make rebuild's source enumeration hash-independent. Cleanest: two passes, no source lookups at all — pass 1: linearly scan the source shadow table's own flat slots; for each (k, stack) entry, `add` the stack entries oldest-first into the new table; pass 2: linearly scan the source's flat slots and `add` each (k, v). Per-key recency is preserved (stack entries are older than the slot binding, which is added last), global order is unspecified anyway. Alternatively: recursively `rebuild` the shadow table first, then do per-slot lookups against the rebuilt shadow. Also state explicitly that resize/copy may keep using hash-directed shadow lookups (they never change the hash function).

## [SERIOUS] add probes with polymorphic compare where stdlib add never calls it — divergence (non-termination / Invalid_argument) on keys stdlib's add accepts

**Scenario:** stdlib generic add (hashtbl.ml:675-680) is a blind prepend: it hashes but NEVER calls compare. Swiss add is an upsert probe that must confirm every h2 candidate with `Stdlib.compare … = 0`. Demonstrated against this toolchain's stdlib: `let rec l1 = 1 :: l1` and `let rec l2 = 1 :: l2` are physically distinct, structurally equal cyclic keys with IDENTICAL polymorphic hashes (verified: both hash to 312056965; `add t l1 "a"; add t l2 "b"; length t = 2; iter` visits both — works fine in stdlib). In Swiss, the second add probes, hits the h2-matching slot, and calls `compare l2 l1`; compare.c's fast path (line 143) requires physical equality, so it recurses structurally on the cycle and NEVER TERMINATES. Same class: compare-equal keys containing physically distinct closures make Swiss add raise Invalid_argument "compare: functional value" while stdlib add succeeds (and iter/fold/length keep working). design.md §3 notes that add probes ("inherent") but does not surface this observable consequence, and §1's non-goals don't list it; api.md §1.4 lists compare-raising as reachable only from find/remove/find_all/replace/mem, not add.

**Fix:** This is inherent to any open-addressing multi-binding scheme and cannot be fixed structurally — promote it to an explicit, documented deviation in §1 non-goals ("add evaluates key equality; keys on which compare diverges or raises are not supported by add, unlike stdlib"), and add the cyclic/functional-key cases to the differential-fuzzer exclusion list (test plan §9 currently says nothing). Optionally narrow the gap with a physical-equality (==) pre-check before compare in the probe loop (free, and makes same-object duplicate adds avoid compare entirely — though compare's own fast path already covers that).

## [SERIOUS] Traversal snapshot discipline is underspecified for filter_map_inplace's WRITES — naive implementation does out-of-bounds unsafe writes when f mutates the table

**Scenario:** The design promises memory safety under mid-traversal mutation (§3 iter: "scan bounds re-checked against the captured arrays, see §6"), and api.md extends iter's comments to filter_map_inplace. But filter_map_inplace writes (vals.(i) <- …, pop-into-slot keys/vals writes, erase via set_ctrl which also writes the mirror byte computed from a mask). Concrete: filter_map_inplace f t where f calls Swiss.reset t (or adds enough keys to resize). reset reallocates ctrl/keys/vals at initial_buckets (e.g. 16 buckets) while the scan is at index i=5000 of the old 8192-bucket arrays. If the implementation routes any post-callback write through the LIVE t.ctrl/t.keys/t.mask (e.g. `set_ctrl i c` using t.mask, or `Array.unsafe_set t.vals i …` justified by §6's "unsafe only after land mask" — land with WHICH mask?), the index 5000 is out of bounds of the 16-slot live arrays: heap corruption via Bytes.unsafe_set/Array.unsafe_set. §6 only addresses iter's READS; nothing pins down the write path.

**Fix:** Specify in §6: every traversal (iter/fold/filter_map_inplace/to_seq stepping) captures (ctrl, keys, vals, mask) as one consistent tuple at entry and routes ALL reads AND writes through the capture, never re-reading t's array/mask fields mid-scan; only the scalar counters (items, nshadow, growth_left) and the shadow table are touched through t. Writes to a stale capture are then lost-but-safe, which is exactly the documented-unspecified-but-memory-safe contract. (A single `mutable core : core` record swapped wholesale on resize/reset — see next finding — makes this capture trivially consistent.)

## [SERIOUS] ctrl/keys split can yield type confusion (dummy `()` read at type 'a) under unsynchronized access — stdlib Hashtbl is structurally type-safe under the same misuse

**Scenario:** stdlib's representation is a single `data` array of immutable-spined cons cells: any racy/interleaved reader dereferences one pointer and sees a well-typed (possibly stale) structure — misuse yields wrong answers, never memory unsafety (the OCaml 5 memory-model guarantee stdlib preserves). Swiss splits the truth across ctrl, keys, vals, mask, updated by multiple non-atomic stores. Two reachable hazards from plain (no-Obj.magic) code that merely violates the unsynchronized_access alert, e.g. two systhreads sharing a table with a missed lock (mode system does not prevent same-domain sys-thread sharing): (a) insert order set_ctrl-then-keys: a poll-point thread switch between the two stores lets a reader see ctrl=FULL while keys.(i) is still the dummy Obj.repr () — Obj.obj returns the unit immediate at type 'a (say string); first use segfaults; (b) resize installs ctrl/keys/vals/mask with several stores: a reader capturing new ctrl (or new mask) with old keys indexes past the old array's bounds through unsafe_get. stdlib cannot produce either failure mode; a drop-in replacement that can is a real safety regression even though the behavior is a documented "programming error".

**Fix:** Two cheap design rules: (1) publish ordering — on insert, write keys.(i) and vals.(i) BEFORE flipping ctrl to FULL; on erase, flip ctrl to EMPTY/DELETED BEFORE dummying the slots (so ctrl=FULL always implies well-typed key/val under per-domain sequential execution); (2) put ctrl/keys/vals/mask in one immutable record behind a single `mutable core` field replaced wholesale on resize/reset, so any single field read yields an internally consistent quadruple. Both are free on the hot path; document residual multi-domain raciness as relying on OxCaml's contention modes.

## [SERIOUS] §5's claim of observable replication with asymmetric `equal` is unachievable, and add's equality argument order is unspecified

**Scenario:** design.md §5: "equality argument order replicated … (API §2.16 — observable with asymmetric equal)". The shadow design structurally cannot deliver result parity for non-equivalence `equal`, and the design never specifies which order its (stdlib-less) add upsert uses. Verified stdlib oracle (Hashtbl.Make, H.equal x _ = (x = A), hash _ = 0; run on this machine): add B 1; add A 2 gives find_opt A = Some 2, find_opt B = None, find_all B = [2], mem B = true. Swiss with stored-first add: `equal B A = false` ⇒ A inserted into a SECOND flat slot; find_opt A (query-first) hits slot0 first: `equal A B = true` ⇒ Some 1 ≠ Some 2. Swiss with query-first add: `equal A B = true` ⇒ shadow push (B,1), slot=(A,2); find_all B (stored-first) hits the slot (`equal A B = true`) and returns the slot value PLUS the whole stack without re-running equal per stack entry ⇒ [2;1] ≠ [2] (stdlib re-tests equal on every cons cell, hashtbl.ml:438-446). Both possible orders diverge; no order can match, because Swiss maintains one-slot-per-key (requires equal to be an equivalence) and returns whole stacks unfiltered.

**Fix:** Re-scope the claim in §5: argument orders of stdlib are replicated within each operation's own probe, and full observable parity is guaranteed only for `equal` that is an equivalence relation consistent with hash (the only sane reading of HashedType); explicitly document non-equivalence equal as unspecified-divergent. Additionally pick and document add's order (query-first is the natural choice — it makes the slot/shadow coalescing match find's notion of 'same key') and decide whether find_all should re-test equal on stack entries (matching stdlib for law-abiding equal either way; not worth the cost — say so).

## [MINOR] create must clamp, never raise — ALG §7's buckets_for_capacity raises Invalid_argument on huge n

**Scenario:** design.md §8 adopts "Sys.max_array_length overflow guard per ALG §7", and ALG §7's buckets_for_capacity does `invalid_arg "capacity overflow"` when cap > max_int/8. api.md §1.4 (verified at hashtbl.ml:81-93): "create raises nothing: any int (including negative) is accepted and clamped" — power_2_above silently stops doubling at Sys.max_array_length. `Swiss.create (max_int/4)` would raise Invalid_argument where stdlib clamps (then fails only with Out_of_memory at allocation, a different and allocation-dependent outcome). Same guard reached via create only — the resize path's capacity argument is bounded by items+1 and can't get there in practice.

**Fix:** In create (and rebuild's sizing), clamp instead of raising: cap exceeding the largest representable capacity yields the largest power-of-two bucket count not exceeding Sys.max_array_length (mirroring power_2_above's stop condition); reserve invalid_arg-free behavior for the public entry points and keep ALG §7's guard as an internal assert/debug check only.

## [MINOR] filter_map_inplace can strand a present-but-empty shadow stack entry — leak and violation of the design's own invariant

**Scenario:** §3 filter_map_inplace step 2 filters the remaining stack ("None drops it, nshadow adjusted") but — unlike remove's pop path — never says the shadow-table ENTRY is deleted when the filtered stack becomes []. Sequence: add k 1; add k 2; filter_map_inplace (fun _ v -> if v = 2 then Some v else None) t — slot (k,2) survives, stack [(k,1)] filters to [], entry k ↦ [] remains. Then remove t k: stack is empty ⇒ slot erased — but the empty entry keyed k stays in the shadow table while k is no longer in the flat table, violating invariant-checker rule §9.3 ("shadow keys all present in flat table") and retaining k forever (GC leak). Not user-observable through the API (iter/stats/find_all read the stack as empty), but the test invariant will fire and the key leaks.

**Fix:** Specify in step 2: if the filtered stack is empty, remove the key's entry from the shadow table (probe key in hand). Defensively, make remove's "stack empty/absent" arm also delete a present-but-empty entry before erasing the slot, and have the invariant checker assert no empty stacks exist.

## [MINOR] The kind ascription `mutable_data with 'a with 'b` will not typecheck over an Obj.t-array representation as the design asserts — needs an explicit unsafe kind-crossing annotation

**Scenario:** design.md §2 claims: "The mli's kind annotation is declared on the abstract type; the record is ordinary mutable data, so this is sound — external code only sees the conservative declared kind." But the kind checker infers the record's kind from its fields, where 'a/'b have been erased to Obj.t (kind value, crossing nothing). The declared `mutable_data with 'a with 'b` crosses contention/portability axes whenever 'a and 'b do (e.g. (int,int) t); the inferred kind of the Obj.t-based record never does, so the inferred kind is NOT a subkind of the declaration and the mli ascription is rejected — the opposite of "conservative". The same issue hits the MakePortable/MakeSeededPortable signatures.

**Fix:** Plan for the OxCaml escape hatch ([@@unsafe_allow_any_mode_crossing] or the current equivalent) on the type definition, and record the actual soundness argument the annotation discharges: every keys/vals slot only ever holds a value of type 'a / 'b or the immediate () dummy (which crosses everything), so the representation genuinely supports `mutable_data with 'a with 'b`. Update §2's rationale accordingly so the implementer isn't surprised.

## [NOTE] Traversals (iter/fold/to_seq/stats/filter_map_inplace) hash-and-probe the live shadow table per duplicated slot — stdlib traversals never invoke hash or equal

**Scenario:** Each FULL slot's stack is fetched by a shadow-table lookup keyed by keys.(i), i.e. a hash + equal probe at traversal time, whenever shadow is Some. Two consequences absent from stdlib (whose iter walks cons cells with zero hash/equal calls, hashtbl.ml:171-187): (1) if a key object is mutated in place after insertion (e.g. a ref/record key), Swiss iter silently misses its shadow stack — length t = 2 but iter visits 1 binding — whereas stdlib iter still visits all bindings and `length` equals the number of f calls (api.md §2.10); (2) every traversal of a duplicate-bearing table pays an extra probe per FULL slot, and user hash/equal (functors) get called from inside iter, observable via side effects/exceptions in user code.

**Fix:** Document both deltas next to the §1 non-goals (mutated keys are folklore-UB in any hash table, but the failure mode differs from stdlib's). Cheap mitigation already available: skip all shadow lookups when shadow = None or nshadow = 0, so non-duplicate tables (the overwhelming case) keep stdlib's zero-hash traversal property.

## [NOTE] rebuild should copy initial_buckets from the source; §3's sizing phrase is garbled

**Scenario:** stdlib rebuild copies initial_size from the source (hashtbl.ml:797), so `reset (rebuild t)` returns to t's original create-time capacity. design.md §3 says rebuild uses "buckets' = max initial-clamp(old buckets)" (unparseable) and never mentions initial_buckets, so a straightforward implementation gives the rebuilt table its own creation size as the reset target — observable only through stats.num_buckets after a later reset (representation-level, not contractual), but it's a gratuitous divergence and the sentence needs fixing regardless.

**Fix:** Specify: rebuilt table gets buckets' = old bucket count (already pow2 ≥ 16, mirroring power_2_above 16 (old buckets)) and initial_buckets copied verbatim from the source, matching stdlib's field-copy behavior.

# Lens: algorithm

Verdict: Sound after fixes. The core algorithm survives the attack: the items/tombstone/growth_left accounting is closed under every operation (shadow pushes/pops leave ctrl untouched and consume no capacity; nshadow is pure bookkeeping), so items + tombstones <= capacity = 7/8·buckets always leaves >= buckets/8 EMPTY bytes and the triangular probe's windows tile the table — termination holds under all op mixes. The remove-with-shadow-pop rule (slot stays FULL, same h2 — valid because equal⇒hash-equal pins h2) never perturbs other keys' probe chains, and the EMPTY-vs-DELETED rule is only ever evaluated at actual ctrl-change time, exactly as in hashbrown. filter_map_inplace's claims check out: deletions never reserve, growth_left is monotone within the scan, and erase's mirror writes land either on the current byte (i>=8) or past the scan bound (buckets+i), so no slot is skipped or re-presented. clear/reset/copy/rebuild field handling and the same-size-rehash trigger arithmetic are correct as specified (the clear no-op shortcut with lingering tombstones is correct since the growth_left debt stays consistent). The two serious findings are not algorithmic: (1) the kind ascription for the Obj.t-array record needs [@@unsafe_allow_any_mode_crossing] or a typed-array wrapper — as written the module does not compile against the mandated mli; (2) the memory-safety promise for captured-array iteration needs an explicit no-scrubbing-of-retired-generations rule plus a FULL-implies-real-slot ordering constraint, otherwise a GC-hygiene-minded implementation of resize produces real segfaults. With those two design additions and the minor reserve/clamping adjustments, the shadow design delivers the contract.

## [SERIOUS] Kind ascription `mutable_data with 'a with 'b` will be rejected for the Obj.t-array record — design's soundness argument addresses the wrong question (design.md §2)

**Scenario:** design.md §2 stores `keys/vals : Obj.t array` and claims "the mli's kind annotation is declared on the abstract type; the record is ordinary mutable data, so this is sound". But signature matching checks that the implementation type's *inferred* kind is a subkind of the declared `mutable_data with 'a with 'b` (api.md §1.1, mli:67). In OxCaml, `Obj.t` is a bare abstract `type t` with no kind annotation (verified: /Users/krystian/code/ocaml-swiss-table/oxcaml/stdlib/obj.mli line 26), so its kind is the non-crossing `value` — an `Obj.t array` may, per the type system, contain closures/uncontended values. Hence `(int,int) Swiss.t` cannot be *proved* to cross modes as `mutable_data` does, and `module Swiss : sig type (!'a,!'b) t : mutable_data with 'a with 'b end = struct type ('a,'b) t = { ...; keys : Obj.t array; ... } end` fails the mode/kind check at compile time. The design as written does not build; "external code only sees the conservative declared kind" is exactly the unsafe claim the checker exists to reject.

**Fix:** Pick and name the escape hatch in the design: attach `[@@unsafe_allow_any_mode_crossing]` to the concrete record (precedent: /Users/krystian/code/ocaml-swiss-table/oxcaml/stdlib/domain.ml lines 215, 257, 338, 526, 580 use it for this exact pattern), with a comment giving the manual proof (only values of type 'a/'b are ever stored via Obj.repr; dummy is the unit immediate). Alternatively type the arrays as `'a array`/`'b array` behind a Uniform_array-style module whose accessors cast through Obj internally — but then re-justify the flambda2 float-specialization concern from §2. Either way §2 must specify the mechanism, not assert soundness.

## [SERIOUS] Memory-safety promise vs retired-array scrubbing: copying resize/rehash must never dummy-out old keys/vals that live iter/to_seq captures may still read (design.md §3 resize, §6)

**Scenario:** iter and to_seq capture `ctrl/keys/vals` references and the design promises memory safety under documented-unspecified mutation (design.md §3 iter/to_seq, §6). §6 also mandates dummy-overwrite "for GC hygiene" on erase, and resize is silent about the retired generation. An implementer extending GC hygiene to resize (scrubbing the old keys/vals after re-insertion — the natural reading of the hygiene rule, and the only case where scrubbing retired arrays even matters is precisely when something still holds them) produces type confusion: `let t = create ~random:false 16 in add t "k" 0; let s = to_seq t in for i = 1 to 20 do add t (string_of_int i) i done (* resize at 15th insert, capacity 14 *); Seq.iter (fun (k,_) -> ignore (String.length k)) s`. The forced seq reads the captured OLD ctrl (still says FULL) paired with a scrubbed OLD key slot = `Obj.repr ()`, then `Obj.obj` presents the unit immediate as a string → `String.length` on an immediate → segfault. Required behavior: anything memory-safe. Same hazard for iter whose `f` triggers a resize, and for the future in-place rehash, which mutates the very arrays a live seq captured and transiently pairs a FULL ctrl byte with a dummy slot.

**Fix:** Add an explicit invariant to §3/§6: (a) retired ctrl/keys/vals generations are never written after replacement (no scrubbing — the GC-hygiene rule applies only to live arrays); (b) on any path where user code can run (H.hash/H.equal/f callbacks, seq forcing), no ctrl byte may read FULL while its key/val slot holds the dummy — constraining the write order of the in-place rehash (slot move completes before the next user-code call site) and of insert (write key/val before or atomically-between with set_ctrl, with no user call between). State that v1 copying resize is exception-atomic (new arrays published only after the loop, all three fields assigned with no user code in between).

## [MINOR] reserve-before-probe in the upsert makes duplicate `add` (and pure-overwrite `replace`) at full load trigger a resize that consumes no slot — correct but wasteful, and it leaks into `rebuild` sizing (design.md §3 add/Resize)

**Scenario:** `create ~random:false 8` → 16 buckets, capacity 14. Add 14 distinct keys → growth_left = 0. Now `add t k1 v'` where k1 already exists: per §3 "`reserve 1` upfront" fires (1 > 0), new_items = 15 > 14/2 → grow to 32 buckets — yet the op only pushes a shadow entry; no EMPTY slot is consumed and growth_left stays untouched by the push. Same for `replace` of an existing key at growth_left=0 (the §3 upsert walk reserves first), and for tombstone-heavy states where a duplicate add triggers a pointless same-size rehash. Consequence chain: `rebuild` re-inserts via `add`; a source table with items = capacity plus ≥1 shadowed binding whose duplicate add lands after the last fresh insert ends up with 2x the buckets stdlib's rebuild analogue would keep. All of this is contract-legal (iteration order unspecified; stats.num_buckets is self-describing and cannot match stdlib anyway) — verified nothing observable diverges — but it is one spurious O(n) copy + permanent 2x memory per crossing, on a path (multi-binding add) stdlib users actually exercise.

**Fix:** Use the probe-first variant ALG §8 already cites (hashbrown raw `insert`, raw.rs L1031-L1043): run the upsert walk without reserving; on key-present, push shadow and return (never reserve); on key-absent, if the chosen slot is DELETED or growth_left > 0 insert directly, else reserve 1 and re-probe. This also removes the duplicate-add rehash hazard entirely since shadow pushes can never trigger resize. If keeping reserve-upfront for hashbrown fidelity, document the waste explicitly and exempt `rebuild` (size the target from source `items`, not via add's reserve).

## [MINOR] Overflow/clamping at giant sizes diverges from stdlib's never-raise behavior, and §8's guard citation is wrong (design.md §8, ALG §7)

**Scenario:** Stdlib `create`/`resize` never raise on size: `power_2_above` stops doubling at Sys.max_array_length and returns the clamp, and `resize` silently no-ops when `nsize >= Sys.max_array_length`, leaving chains to grow while every op keeps working (verified at /Users/krystian/code/ocaml-swiss-table/oxcaml/stdlib/hashtbl.ml lines 80-83, 160-169; api.md §1.4 "create raises nothing", §2.7). Design §8 says "Sys.max_array_length overflow guard per ALG §7" — but ALG §7's guard is `cap > max_int/8` (≈2^59), which has nothing to do with Sys.max_array_length = 2^46−1 (api.md §2.2). So e.g. `create (1 lsl 50)` passes the ALG guard, computes 2^51 buckets, and `Array.make` raises `Invalid_argument "Array.make"` where stdlib clamps to 2^45 buckets (then OOMs on allocation — a different, documented exception). Worse in kind: at the 2^45-bucket ceiling with capacity exhausted, our `add` must raise (a Swiss table cannot run at load 1) while stdlib's `add` keeps succeeding degraded. Practically unreachable (≈half a petabyte of arrays), so minor — but the design text is internally wrong about which guard it has.

**Fix:** Replace the §8 citation with a real rule: clamp `buckets_for_capacity` results to the largest power of two ≤ Sys.max_array_length (create and resize), make resize a no-op... which is impossible for Swiss at 7/8 load — so instead document the hard wall: at max buckets with growth_left = 0 and no tombstones to purge, raise a documented exception (Out_of_memory is the most stdlib-faithful choice since stdlib would have OOMed long before). Keep ALG §7's max_int/8 arithmetic-overflow guard as a separate, earlier check.

## [NOTE] Non-equivalence `equal` diverges observably from stdlib, and the design never pins which equality argument order `add`'s existence probe uses (design.md §3 add, §5)

**Scenario:** §5 advertises argument-order replication as "observable with asymmetric equal", implying fidelity at that level — but stdlib's `add` calls NO equality at all (blind prepend, verified ml:675-680), while the shadow design's `add` must probe with some order the design doesn't specify. With H.hash a = H.hash b, H.equal a b = true, H.equal b a = false: stdlib `add t b v1; add t a v2; remove t b` removes (a,v2) via stored-first `H.equal a b = true`, so `find_opt t a` → Some v1; Swiss `add t a v2` probes (say stored-first: `H.equal b a` = false) → separate slot, `remove t b` finds slot b first in probe order and removes (b,v1), so `find_opt t a` → Some v2. Divergent results from a legal-per-mli H (the HashedType contract only requires equal⇒hash-equal). No keyed structure other than a recency list can match stdlib here, since stdlib's behavior depends on bucket interleaving across equivalence classes.

**Fix:** Two-line addition to §1 non-goals: behavior matches stdlib only when `equal` is an equivalence relation (and `compare`-equality is one by construction in the generic interface — note nan-with-(=) functors still match, since neither implementation ever groups irreflexive keys). And pin add's order in §3 — stored-key-first, consistent with the remove/replace/mem family it shares the upsert walk with — so the differential fuzzer has a defined target.

## [NOTE] iter/fold/to_seq/stats hash every FULL slot's key through the shadow-table lookup once any duplicate exists — stdlib's traversals never call the hash function (design.md §3 iter)

**Scenario:** §3 iter: "for FULL slot: visit (keys.(i), vals.(i)), then each (k_j, v_j) of its shadow stack" — finding "its shadow stack" is a keyed lookup in the shadow Swiss table, i.e. one H.hash (or caml_hash_exn) call plus a probe per FULL slot, for every traversal, whenever `shadow = Some _`. Stdlib's iter/fold/to_seq/stats/filter_map_inplace never hash (they walk the bucket array; /Users/krystian/code/ocaml-swiss-table/oxcaml/stdlib/hashtbl.ml ml:171-187). Observable only with impure/raising H.hash (stateful hash that succeeds during add but raises later makes Swiss's iter raise where stdlib's succeeds) — pathological, so note-level; the real cost is O(n) extra hashing on every traversal of a table that ever held one duplicate, including after the duplicates are all removed (shadow stays Some(empty)).

**Fix:** Document the cost and bound it: reset `shadow` to None when `nshadow` returns to 0 (cheap check in remove/filter_map_inplace), so only tables with live duplicates pay; gate the per-slot lookup on `nshadow > 0`, not on `shadow <> None`. Optionally note the invariant for tests: traversal does zero hash calls when nshadow = 0.

Two findings need design changes before implementation: (1) the §2 kind-soundness argument is factually wrong — the exact record is rejected against the mirrored mli kind annotation; the verified fix is the stdlib-idiom `[@@unsafe_allow_any_mode_crossing]` with an explicit kind on the .ml declaration; (2) the probe loops need an explicit snapshot discipline for ctrl/keys/vals/mask, because reentrant functor equal/hash (reset/resize from inside the loop) plus the §6 'unsafe after land mask' rule yields out-of-bounds unsafe accesses that stdlib does not have. Both fixes are localized and compiler-verified; with them, plus the smaller amendments (build-then-commit resize, stdlib-style create clamping, polymorphic-recursion layering, and the documented Pgenarray access cost), the design is implementable as specified.

## [SERIOUS] §2 kind-annotation soundness argument is false: the design's exact type declaration is rejected at mli/ml matching

**Scenario:** Verified by compilation (/tmp/oxdesign/k1) with /Users/krystian/code/ocaml-swiss-table/oxcaml/result/bin/ocamlopt.opt: mli `type (!'a, !'b) t : mutable_data with 'a with 'b` (the verbatim hashtbl.mli line the design must mirror) against the §2 record with `keys/vals : Obj.t array` and `shadow : ('a,'b) shadow` fails: "The kind of the first is mutable_data with ('a, ('a * 'b) list) t ... with Obj.t ... The first mode-crosses less than the second along: portability ... statefulness". `Obj.t` is bare `type t` (oxcaml/stdlib/obj.mli:26, kind `value`, crosses nothing), so any record containing `Obj.t array` cannot satisfy `mutable_data with 'a with 'b`. The design's claim that "the record is ordinary mutable data, so this is sound — external code only sees the conservative declared kind" is wrong: OxCaml signature matching checks the declared kind against the inferred kind of the implementation; declaring it only in the mli does not help.

**Fix:** Verified working (/tmp/oxdesign/k2 and full integration /tmp/oxdesign/integ compile clean, including `@@ portable` mli + alert block): put the kind on the .ml declaration and assert it: `type ('a,'b) t : mutable_data with 'a with 'b = { ... } [@@unsafe_allow_any_mode_crossing "Obj.t slots only ever hold 'a / 'b values"] and ('a,'b) shadow = ('a, ('a*'b) list) t option`. This is the established stdlib idiom (used in oxcaml/stdlib/domain.ml:215,257,338,526,580, semaphore.ml:25). It is genuinely sound here: the Obj.t slots only ever contain 'a keys, 'b values, ('a*'b) list stacks, or the unit dummy. (Side fact, also verified /tmp/oxdesign/k3: with typed `'a array`/`'b array` fields the kind check passes even with the recursive shadow field — the blocker is specifically Obj.t — but the design's reason for rejecting typed arrays is validated: this build has flat_float_array: true, so the float-specialization hazard is real.) Update §2's soundness paragraph accordingly.

## [SERIOUS] Probe loops are memory-unsafe under reentrant table mutation from functor H.equal/H.hash; §6's 'unsafe only after land mask' rule is insufficient

**Scenario:** Well-typed user code, no Obj, no unsafe: `module H = struct type t = int let hash = Hashtbl.hash let equal a b = (if !armed then T.reset (Option.get !self)); a = b end; module T = Swiss.Make(H)`. Grow t to 2048 buckets (mask=2047), set `self := Some t; armed := true`, call `T.find t k` on a populated chain. The probe loop caches `mask = 2047` in a local at entry (every reasonable implementation does); the first `H.equal` call resets t, replacing t.keys with a 16-element array. If the loop then re-reads `t.keys` (the natural field-access-per-iteration style) and executes `Array.unsafe_get t.keys ((pos+off) land 2047)` — exactly what §6 sanctions, since the index IS masked — it reads up to index 2047 of a 16-element array: out-of-bounds heap read, reinterpreted via Obj.obj — possible segfault or type-confused value. The same hazard exists in the insert path (writes through stale ctrl/mask after eq-triggered resize, corrupting counters → growth_left wrong → unbounded probe loop). Stdlib under the identical program is memory-safe (it walks a captured bucket-list spine; resize/reset never invalidates indices it holds). The design promises memory safety under mutation for iter (§3, §6 'captured arrays') but says nothing for find/add/replace/remove/mem/find_all probe loops, where user code (H.equal, H.seeded_hash) runs mid-loop.

**Fix:** Add a snapshot discipline to §6: every operation loads ctrl, keys, vals, mask into locals exactly once at entry (after the upfront reserve, for inserts) and never re-reads the record fields after any user-code call (eq/hash); all reads AND writes go through the snapshot, so a reentrant resize/reset leaves the op working on the orphaned-but-intact old arrays (memory-safe, semantically unspecified — matching stdlib's de-facto behavior). For mutating ops, either re-check `t.keys == snapshot_keys` (physical equality) before committing counter updates (items/growth_left/nshadow), restarting the op if it changed, or document that counters may be stale after reentrant abuse but bound the damage: keep the debug `stride <= buckets` assert in release as a raise (cheap, once per group step) so a counter-corrupted table raises instead of looping forever.

## [MINOR] Copying rehash/resize must build-then-commit, or a raising functor hash mid-resize leaves the table incoherent (contradicts §6's coherence claim)

**Scenario:** MakeSeeded with an H.seeded_hash that raises after N calls (e.g. reads a counter ref). Table at growth_left = 0 with 14 items; `T.add` → reserve → resize. If resize assigns t.ctrl/t.keys/t.vals/t.mask to the fresh arrays before re-inserting the 14 slots (hashbrown's order, and stdlib's: ml resize sets h.data before insert_all_buckets), the raise on key 3 propagates out of add leaving t.items = 14 but only 2 entries present: length lies, 12 bindings silently lost, growth_left stale → later inserts can probe a table whose accounting is wrong. Stdlib also loses bindings in this scenario, but §6 explicitly promises 'internal state must stay coherent', which this ordering violates.

**Fix:** One sentence in §3-Resize/§6: copying rehash fully populates the fresh ctrl/keys/vals and computes the new growth_left BEFORE assigning any record field; the field assignments are the last, non-raising step (single commit). A user-hash raise mid-rehash then leaves the old table fully intact — strictly better than stdlib, and free.

## [MINOR] create's overflow behavior diverges from stdlib, and ALG §7's guard doesn't even cover the reachable failure

**Scenario:** Stdlib `Hashtbl.create` never raises (api.md §1.4): power_2_above clamps doubling at Sys.max_array_length (= 2^46−1 in this runtime, so max 2^45 buckets) and the worst case is Out_of_memory from Array.make. Design §8 adopts ALG §7's `buckets_for_capacity`, which (a) raises Invalid_argument "capacity overflow" for cap > max_int/8 = 2^59 — an exception stdlib's create can never raise — and (b) for n in (7·2^45/8 .. 2^59] passes the guard but computes buckets ≥ 2^46 > Sys.max_array_length, so `Array.make` raises Invalid_argument "Array.make": e.g. `Swiss.create (1 lsl 47)` raises Invalid_argument while `Hashtbl.create (1 lsl 47)` clamps to 2^45 buckets and OOMs. Same applies to the resize growth target.

**Fix:** Mirror stdlib's clamp-never-raise shape in §8: cap buckets at the largest power of two b with 2·b ≤ Sys.max_array_length (i.e. 2^45 here) instead of raising; let Array.make/Out_of_memory be the only failure mode, as in stdlib. Drop the invalid_arg from buckets_for_capacity in the create path (keeping it as an internal debug assert is fine).

## [MINOR] Functions that recurse into the shadow table need explicit polymorphic-recursion annotations (design is silent)

**Scenario:** Verified (/tmp/oxdesign/pr): the natural `let rec copy t = { ... shadow = Option.map copy t.shadow }` over the §2/§3 types is rejected: "This expression has type ('a, 'b) shadow = ('a, ('a * 'b) list) t option but an expression was expected of type ('a, 'b) t option / The type variable 'b occurs inside ('a * 'b) list" — the shadow type is non-regular, so any function reaching t at the shadow instance from itself needs polymorphic recursion. ## [NOTE] iter/fold/to_seq call the hash function mid-traversal once any duplicate exists — stdlib's never do

**Scenario:** §3 iter looks up 'its shadow stack' per FULL slot, which is a probe of the shadow table = a hash call per slot whenever shadow ≠ None. Stdlib iter/fold/to_seq never invoke H.hash/caml_hash_exn. Observable divergence with a side-effecting or raising user hash: `module H = struct ... let hash x = incr count; Hashtbl.hash x end` — after one duplicate add, `T.iter` bumps `count` per visited key (stdlib: zero); a hash that raises makes our iter raise where stdlib's completes. All within 'unspecified' territory but a real differential-fuzzer tripwire.

**Fix:** Either document it as an accepted divergence (and exclude side-effecting hash from the §9 oracle comparison), or avoid it: emit all flat slots first, then walk the shadow table's own slots emitting each stack in order — the documented per-key most-recent-first guarantee still holds (slot binding precedes its stack entries; stack is ordered), no hashing needed, and only filter_map_inplace keeps the interleaved pop-into-slot logic.

## [NOTE] clear's no-op shortcut keyed on emptiness leaves tombstones and stale growth_left

**Scenario:** add/remove churn until items = 0 with DELETED bytes present and growth_left < capacity (possible: removes that erase to DELETED don't restore growth_left). `clear t` with shortcut condition items=0 ∧ nshadow=0 skips the ctrl refill, leaving tombstones; table is semantically empty (correct) but the next insert immediately triggers a same-size rehash — unlike stdlib clear, which always leaves pristine buckets. **Fix:** Make the shortcut condition `growth_left = capacity_of_buckets buckets && nshadow = 0` (true emptiness, including no tombstones), or unconditionally refill ctrl when items=0 but growth_left < capacity.
