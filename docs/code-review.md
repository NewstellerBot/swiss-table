## [SERIOUS] (algorithm) Hot paths allocate per operation: flambda2 does not eliminate the probe-loop closures (10 minor words per find/mem, 25 per replace) — contradicts design §2's 'verified allocation-free' claim

**Location:** Engine.find_idx_query / find_idx_upd / upsert_idx (lib/swiss.ml lines 292–373); same pattern in find_insert_fresh (239–251)

**Argument:** Design §2 (Group abstraction) states 'REV verified the whole find loop compiles allocation-free and fully unboxed under flambda2'. This is false for the shipped artifact. Measured against the dune-built swiss.cmxa (flambda2: true toolchain, both default and release profiles) with Gc.minor_words around tight loops of 100k–200k int-keyed ops: Swiss MakeSeeded mem/find/find_opt = 10.00 minor words/op, generic Swiss.mem = 10.00, replace of an existing key = 25.06, while stdlib Hashtbl.MakeSeeded mem/find = 0.00 and bare seeded_hash = 0.00. Assembly (ocamlopt.opt -O3 -S of swiss.ml) shows the cause exactly: camlSwiss__find_idx_query's prologue bumps the allocation pointer by 80 bytes (`sub x27, x27, #80` = 10 words) and builds a caml_curry2 closure for `group_loop` capturing tag/mask/ctrl/keys/key on EVERY call, before tail-branching into it; the upsert path allocates ~25 words/op the same way. The SWAR arithmetic itself is fine — the loop body is fully unboxed in registers (single madd/eor/sub/and chain, no int64 boxing, no per-group allocation: misses with longer probes still measure exactly 10.00) — it is purely the `let rec group_loop … let rec match_loop …` nest that survives closure conversion as a heap closure. This is invisible to the differential fuzzer and unit tests (semantics are correct; Swiss even beats stdlib in the CPU-time microbench: find-hit 22.5 vs 24.9 ns/op, miss 9.1 vs 33.0 ns/op) but produces 80 B of garbage per lookup and ~200 B per update — a minor-GC cycle every ~26k lookups at the default minor heap, pure overhead vs stdlib's zero-allocation read path, in a project whose stated purpose is performance.

**Fix:** Restructure the three probe walks (and find_insert_fresh/erase if affected) so no local recursive closure capturing the snapshot survives: either (a) rewrite as `while`-loops over mutable locals (pos/stride/m as int refs that flambda2 demotes to registers, g rebound per iteration), or (b) make group_loop/match_loop top-level [@inline]-ed functions of the Engine functor taking ctrl/keys/mask/tag/key as explicit parameters so they compile as static-call loops with no environment. Re-verify with the Gc.minor_words probe (expect 0.00 words/op for mem/find on int keys) and by grepping the -S output of find_idx_query for `sub x27`/caml_call_gc.

## [NOTE] (algorithm) max_buckets hard wall does not raise Out_of_memory as design §8 specifies; growth_left goes negative and the table degrades to O(n)-rebuild-per-insert ending in Invalid_argument

**Location:** reserve_grow / insert_absent (lib/swiss.ml lines 377–423) with buckets_for_capacity clamp (198–201)

**Argument:** Design §8: 'The hard wall (insert at max_buckets with growth_left = 0, no tombstones) raises Out_of_memory.' The code never implements this raise. Trace at buckets = max_buckets (2^45), items = capacity = 7·2^42, growth_left = 0, no tombstones: insert_absent sees an EMPTY target and growth_left = 0, calls reserve_grow; items+1 > full_cap/2 so nb = buckets_for_capacity (full_cap+1), which hits the `cap >= capacity_of_buckets max_buckets` clamp and returns max_buckets again; a full same-size copying rehash runs (nothing to purge), growth_left is recomputed to capacity − items = 0, and do_insert then consumes an EMPTY slot, setting growth_left to −1. This breaks the documented invariant growth_left = capacity − items − tombstones (which design §9 says the invariant checker enforces), every subsequent EMPTY-consuming insert re-triggers a full 2^45-slot core rebuild (O(n) per insert), and once all buckets are FULL the probe loops raise Invalid_argument "Swiss: probe invariant violated" instead of Out_of_memory. Unreachable in practice — it requires ~3·10^13 live entries (~0.7 PB of slot arrays), which is why no test or fuzzer can ever see it — but it is a concrete deviation from the design's stated behavior at the clamp boundary.

**Fix:** In reserve_grow, after computing nb, add: `if capacity_of_buckets nb <= t.items then raise Out_of_memory` (equivalently, raise when nb = max_buckets and no headroom remains), before allocating the new core. This implements design §8's wall, keeps growth_left nonnegative, and preserves the invariant checker's contract.

**Verifier (note):** CONFIRMED by code inspection and a compiled scaled-down reproduction. (1) Spec: design.md §8 (lines 310-312) explicitly states "The hard wall (insert at max_buckets with growth_left = 0, no tombstones) raises Out_of_memory", and design-review.md line 91 shows this was a deliberate, review-mandated design decision. (2) Code: grep finds no Out_of_memory raise anywhere in lib/swiss.ml; reserve_grow (377-397) just clamps via buckets_for_capacity (198-201) and recomputes growth_left, and insert_absent (416-423) unconditionally inserts after the same-size rehash. (3) Reproduction: compiled lib/swiss.ml verbatim under the OxCaml toolchain with only max_buckets forced to 32 plus debug accessors (/tmp/oxwall_probe). At items = capacity = 28, growth_left = 0, no tombstones: insert 29 raises nothing, performs a full same-size core rebuild, and leaves growth_left = -1; inserts 30-32 each trigger another full core rebuild (verified by core physical identity — O(n) rebuild per insert) with growth_left descending to -4; once all 32 slots are FULL, insert 33 AND even mem of an absent key raise Invalid_argument "Swiss: probe invariant violated" — marginally worse than claimed, since absent-key lookups break too. The proposed fix was checked against reserve_grow's other paths (same-size tombstone purge, uncapped growth) and fires only at the genuine wall. Refutation attempts failed: the file-header comment "design §8: clamp, never raise" covers only the sizing function, not the wall; incidental allocation OOM on real hardware is not the specified behavior; and the test invariant checker (test_unit.ml:160) checks only the sum equation growth_left + items + tombstones = 7/8·buckets, which still holds at negative growth_left, so nothing guards this state. Severity 'note' stands: the state needs ~7·2^42 live entries (petabytes of slot arrays), unreachable by any test, fuzzer, or real workload, and physically realizable executions would hit allocation Out_of_memory inside make_core first; it is nonetheless a concrete, reproducible deviation from the design's stated hard-wall behavior.

## [MINOR] (unsafe) Reentrant mutation of the SAME (un-swapped) core corrupts items/growth_left/nshadow; the t.c==c guard only catches whole-core swaps

**Location:** erase commit lib/swiss.ml:267-270; do_insert commit 408-411; add nshadow 488; shadow_pop_into commit 469-472; filter_map stack-phase 591-594; reserve_grow unguarded commit 396-397

**Argument:** Design §2 claims the t.c==c guard keeps "state coherent w.r.t. the live core." It does not. The guard only detects a wholesale core SWAP (reset/resize). When a reentrant callback (user eq/hash/f) commits a slot-level change to the SAME live core that the outer op will also commit to, both commits fire (both see t.c==c true) and double-count. Concretely, an outer `remove k` whose `equal` reentrantly calls `remove k` again: the inner erase flips the slot and does items-- / growth_left++; the outer walk's eq still returns true so it erases the now-empty slot AGAIN, doing items-- / growth_left++ a second time. DEMONSTRATED via Swiss.Make with a self-reentrant equal: a single-binding table ends with items=-1, growth_left=29 > capacity=28, length=-1. The fuzzer excludes reentrancy from its oracle, and the reentrancy-smoke unit tests only fire reset/clear bombs (reset swaps the core so the outer commit is skipped; clear scrubs in place but resets counters consistently so a single subsequent insert stays coherent — verified: clear-bomb leaves items=15, 15+13=28=cap). No existing test constructs a reentrant slot-level commit to the same core, and the invariant checker's `items == FULL-count` check (test_unit.ml:158) would catch it but is never run on this state. The growth_left invariant `growth_left+items+tombstones = 7/8·buckets` still holds NUMERICALLY (both drift together), so even that checker passes. Damage is BOUNDED, not heap corruption: every unsafe index is masked, so do_insert/erase never write out of bounds; inflated growth_left only delays resize, and a genuinely full table raises probe_invariant_failure (Invalid_argument) instead of looping — confirmed by driving 100k inserts after the drift with no crash (a persistent off-by-one length). The escalated consequence is a delayed spurious Invalid_argument from later well-behaved code if accumulated drift ever exceeds the EMPTY headroom (buckets/8).

**Fix:** The t.c==c physical-equality guard is necessary but insufficient. Either (a) document that reentrant mutation may leave counters incoherent (drop the "coherent w.r.t. live core" claim in §2/§6), or (b) make erase/do_insert idempotent w.r.t. their own commit by checking the slot's pre-state under the guard — e.g. erase should only commit items--/growth_left++ when the ctrl byte it is flipping was actually FULL on entry (read it before set_ctrl and gate the counter update on that), and do_insert already reads was_empty but should also gate items++ on the slot not already being FULL. That bounds the per-slot commit to once regardless of nested re-entry on the same core.

**Verifier (minor):** Confirmed by direct reproduction with a compiled probe against the built library. (1) Mechanism verified in /Users/krystian/code/ocaml-swiss-table/swiss/lib/swiss.ml: the commit guards at erase (267-270), do_insert (408-411), add (488), shadow_pop_into (469-472), and filter_map_inplace (591-594) test only physical equality `t.c == c`, which detects whole-core swaps (reset/resize) but not slot-level reentrant mutation of the same core; reserve_grow (396-397) commits unguarded. (2) Reproduction (/tmp/oxverify/probe_reentrant.ml, compiled with the oxcaml toolchain against _build/default/lib/swiss.cmxa): a Swiss.Make instance whose equal fires one reentrant `remove` of the same key yields items=-1, growth_left=15 > capacity=14, length=-1 after a single outer remove — both erase commits fire because no core swap occurred. Damage is bounded exactly as claimed: 100k subsequent well-behaved replaces ran without exception, leaving a persistent off-by-one length that survives resizes. (3) Escalation verified (/tmp/oxverify/probe_escalate.ml): two reentrant removes accumulate drift 2 = buckets/8 EMPTY headroom on a 16-bucket table; 16 purely well-behaved adds then fill all 16 slots FULL (inflated growth_left suppresses resize), after which well-behaved mem/find_opt of an absent key raise Invalid_argument("Swiss: probe invariant violated") while present-key lookups succeed — a spurious exception from later correct code, exactly as the claim predicted. (4) The "documented as unspecified" defense fails: docs/design.md §2 (snapshot discipline) explicitly claims the commit-check keeps "state coherent w.r.t. the live core" and §6 rule 1 lists it as a safety rule; the probe falsifies that coherence claim (live core has 0 FULL slots, items=-1). (5) Test-coverage assertions check out: test_unit.ml section 9 reentrancy-smoke only fires reset/clear bombs (reset swaps the core so the guard works; clear scrubs in place but resets counters consistently, so the single outer commit stays coherent); the invariant checker line that would catch this (test_unit.ml:158, "inv: items <> number of FULL ctrl bytes") is never run on such a state; the fuzzer (test_diff.ml:31-33) excludes non-equivalence/side-effecting callbacks from its oracle. The claim's auxiliary detail also holds: growth_left+items+tombstones stays numerically consistent (both counters drift together), so that checker line passes while the FULL-count check would fail. No refutation found; the argument is airtight and the proposed fixes (document the limitation, or gate per-slot commits on the slot's pre-state) are apt.

## [MINOR] (contract-perf) h2 extraction from bits 23–29 nullifies SWAR tag filtering for the mli's own recommended functor hash (identity int hash) on keys < 2^23

**Location:** h2_of_hash (lib/swiss.ml:226) + functor hash masking (975-976); mli example at lib/swiss.mli:329-334

**Argument:** h2 = (h lsr 23) land 0x7f. The Swiss mli (copied from stdlib) recommends 'let hash i = i land max_int' for int keys. With that hash every key < 2^23 = 8.4M has h2 = 0, so all FULL ctrl bytes are 0x00 and Group.match_byte matches every full slot in every probed group — each one costing a (currently indirect, Finding 2) eq call. Counting probe (N=100k random keys < 2^23, Swiss.Make with counting equal): 2.43 eq calls per successful find with the identity hash vs 1.01 with Hashtbl.hash — a 2.4x eq inflation that exists for exactly the hash function the documentation recommends, and that stdlib is immune to (it uses only low bits, which identity hashes populate well). Today the cost is masked by the Finding-1/2 overheads (find hit 16.4 ns identity vs 17.3 ns mixed because identity skips the caml_hash C call), but after those are fixed this becomes the limiting factor for the most common custom-hash pattern. The ALG §3 analysis only covers the >2^23-buckets overlap case for well-mixed 30-bit hashes; it does not cover low-entropy user hashes, where the rejected cheap mixer would actually help.

**Fix:** Either (a) document loudly in Swiss's HashedType/SeededHashedType docs that, unlike stdlib, hash quality in bits 23-29 matters and identity-style hashes degrade tag filtering (and change the mli's IntHash example to a mixing hash), or (b) apply a single-multiply finalizer (e.g. h * 0x2545F4914F6CDD1D land 0x3FFF... then split, constant fits 63-bit) to FUNCTOR-provided hashes only, keeping the generic path (already Murmur3-finalized) unmixed; option (b) costs one multiply per op and removes the failure mode entirely.

**Verifier (minor):** Attempted refutation failed; claim verified end-to-end with a compiled counting probe (bench/h2probe.ml, runnable via `$DUNE exec bench/h2probe.exe`).
